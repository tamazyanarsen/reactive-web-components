# Версии UI-кита в микрофронтендах

[English](../en/microfrontends.md) · [Гайд](./guide.md) · [Рецепты](./recipes.md)

Платформа из независимо выкатываемых модулей обычно живёт на одном UI-ките. С
веб-компонентами здесь есть жёсткое ограничение: имена тегов глобальные. Если
`<ui-button>` уже определён, второй `customElements.define("ui-button", ...)` бросит
исключение. Поэтому вся платформа привязана к одной версии кита, и обновить кит можно
только согласованным релизом всех модулей.

rwc снимает это ограничение, не трогая код модулей. Компонент объявляется один раз, а
регистрируется под тегом, который выбирает тот, кто его подключает. Разметка обращается к
компоненту через фабрику, а не через имя тега.

объект кита, который ей передают.

## Как это устроено

Кит объявляет компоненты и экспортирует фабрики вместе с функцией регистрации:

```ts
// @acme/ui-kit
import { configCustomComponent } from "@rwcjs/core";

export const [UiButton, registerUiButton] = configCustomComponent(Button, "ui-button");
export const [UiModal, registerUiModal] = configCustomComponent(Modal, "ui-modal");

export const registerAll = (options?: { postfix?: string }) => {
  registerUiButton(options);
  registerUiModal(options);
};
```

Каждый модуль регистрирует ту версию кита, с которой собран:

```ts
// биллинг, ещё на ките 1.7
import { registerAll, UiButton } from "@acme/ui-kit-1.7";
registerAll({ postfix: "v1-7" });   // <ui-button-v1-7>, <ui-modal-v1-7>

// профиль, уже на ките 1.8
import { registerAll, UiButton } from "@acme/ui-kit-1.8";
registerAll({ postfix: "v1-8" });   // <ui-button-v1-8>, <ui-modal-v1-8>
```

Код модулей одинаковый, потому что вызывает фабрику:

```ts
UiButton({ ".variant": "primary", "@click": save }, "Сохранить");
```

Модули переезжают на новый кит по одному. Модуль на 1.8 можно отрисовать внутри модуля на
1.7: каждый компонент создаёт детей фабриками своего кита.

## Постфикс по версии кита, а не по модулю

`customElements` разрешает зарегистрировать класс только под одним тегом. Если два модуля
делят одну копию кита (например, синглтон в Module Federation) и регистрируют её с разными
постфиксами, второй вызов не может создать второй тег: rwc оставляет первый и пишет ошибку
в консоль.

Поэтому называйте постфикс по версии кита. Тогда модули на одной версии делят один набор
тегов, повторные `registerAll({ postfix: "v1-8" })` ничего не делают, а по тегу в DOM видно,
какая версия кита его отрисовала.

Оболочка может держать самый новый кит без постфикса, тогда в её разметке обычные имена.

## Правила для авторов кита

Кит безопасен для нескольких версий, если внутри ничего не зависит от точного имени тега:

- **Композиция через фабрики.** Диалог, в котором есть кнопка, вызывает `UiButton(...)`, а
  не `document.createElement("ui-button")`.
- **Детей искать по классу, а не по тегу.** Слотовые элементы фильтруются через
  `el instanceof Tab`, а не через `el.localName === "ui-tab"` или `querySelector("ui-tab")`.
- **Сгенерированным id — префикс из тега.** У каждой копии кита свой счётчик id, и он
  начинается с нуля, так что `ui-tab-1` появился бы на странице дважды. Используйте
  `` `${this.localName}-${++counter}` ``: в теге уже есть постфикс. `@rwcjs/ui` так делает
  во вкладках и подсказках.
- **Хост стилизуется через `:host`, а не селектором тега.** Внутри компонента
  `ui-button { ... }` не совпадёт с `ui-button-v1-8`.
- **Тег, если он нужен, брать из класса.** После регистрации в `Component.renderTagName`
  лежит настоящий тег. `toast()` в `@rwcjs/ui` создаёт по нему контейнер уведомлений.

## Правила для авторов модулей

- Не пишите имена тегов в CSS и тестах. Компоненты стилизуются через CSS-переменные,
  `::part()` и классы на хосте, а в тестах ищутся по роли или `data-testid`.
- Переменные темы (`--rwc-*` в `@rwcjs/ui`) наследуют все версии кита на странице. Бренд
  остаётся единым, но релиз кита, который переименовывает переменную, должен держать старое
  имя, пока не обновится последний модуль.
- Несколько сборок кита могут делить одну копию `@rwcjs/core`; какие версии ядра кит
  принимает, решает его `peerDependencies`.

## Сравнение со scoped custom element registries

[Scoped custom element registries](https://developer.chrome.com/blog/scoped-registries) —
ответ платформы на ту же проблему: у теневого корня свой реестр, и один и тот же тег в разных
частях страницы может означать разные классы. Они есть в Chrome и Edge 146 и в Safari 26, но в
Firefox пока только за флагом ([caniuse](https://caniuse.com/wf-scoped-custom-element-registries)).

| | Постфиксы rwc | Scoped registries |
| --- | --- | --- |
| Браузеры | Везде, где работают custom elements | Chrome/Edge 146+, Safari 26+; Firefox за флагом |
| Где можно смешивать версии | Где угодно, включая light DOM | Внутри теневых корней со своим реестром |
| Тег в DOM | Свой у каждой версии (`ui-button-v1-8`) | Один тег, разные классы |
| Код, создающий элементы | Фабрики, без изменений | Должен создавать элементы в нужном реестре |

Подходы не конфликтуют. Когда scoped registries появятся во всех браузерах, которые
поддерживает платформа, регистрацию можно будет перевести на них, и код модулей, который
вызывает только фабрики, менять не придётся.
